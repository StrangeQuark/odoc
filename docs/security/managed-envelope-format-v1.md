# Managed envelope and chunk framing format v1

**Owner:** P0-016; production adapter: P1-115  
**Status:** interface specification and test-vector baseline, not a production implementation

## Record envelope

The managed profile uses maintained platform/provider primitives only:

- AES-256-GCM for individual bounded records;
- AES-KW-256 or a KMS/HSM provider wrap operation for DEK wrapping; and
- CSPRNG nonces generated by the cryptographic provider.

The envelope-v1 and key-wrap-v1 vectors are executed in both Java and browser test
suites. Test keys are public and must never be accepted in a runtime profile.

Each encrypted record stores an algorithm/version identifier, key version, nonce,
ciphertext-with-tag, and a canonical associated-data encoding. Associated data is
the complete tuple below, serialized deterministically with unambiguous field lengths
before encrypt/decrypt:

    formatVersion, algorithm, securityScopeKind, securityScopeId,
    resourceId, purpose, plaintextSchemaVersion, keyVersion

Wrong scope, resource, purpose, schema, or key version must fail authentication; the
caller receives no partial plaintext or crypto diagnostic. Records larger than the
approved record limit use the object format below, never a homemade streaming-GCM
construction with one final tag.

## Large-object framing

An encrypted object has an authenticated manifest and independently authenticated
chunks. The manifest records format/version, object ID, scope, purpose, DEK key
version, plaintext length, chunk size/count, nonce prefix, and ordered chunk digests.
Each chunk's AAD includes manifest identity, object ID, chunk index, chunk count,
declared plaintext length, scope, purpose, envelope version, and key version. Its
96-bit AES-GCM nonce is random 64-bit object prefix plus uint32be(chunk index); a hard
count limit prevents reuse for one DEK/object pair.

A reader authenticates the manifest first, authenticates a requested chunk before
emitting any byte, verifies final count/length, and rejects reordered, duplicated,
deleted, spliced, truncated, or cross-object chunks. Range reads align to verified
chunks and discard non-requested edge bytes only after authentication. Cancellation
removes staged ciphertext and never turns an unauthenticated prefix into output.

The shared `chunked-object-v1` feasibility vector is verified by Java JCA and browser
WebCrypto. It authenticates the manifest before reconstruction, reassembles the
ordered chunks, demonstrates a range after verified reconstruction, and rejects a
missing chunk, reordered chunk, changed ciphertext, and changed scope. P1-115 must
extend this baseline with production-adapter vectors for duplicate/delete/splice/
truncation, cancellation, rotation, and all streaming-range edge cases before the
object adapter is used for customer data.

## Lifecycle and failure policy

DEKs are purpose- and scope-scoped. Rotation adds a new active key version, rewraps
DEKs where supported, then re-encrypts records/objects through resumable, fenced jobs.
A disabled or compromised version blocks fresh encryption and reads according to the
incident policy. Crypto-shredding deletes the wrapping authority only after
retention/legal-hold checks; it is irreversible. Key backups are held under a separate
recovery authority from data backups, and restore drills use dummy external credentials
so restored queues cannot send live traffic.

The binary/JSON storage representation may evolve only through a new version, test
vectors, a reader compatibility window, and a migration/rollback plan. The future
zero-knowledge profile has its own protocol and must not reuse managed server-held
content keys as a shortcut.
